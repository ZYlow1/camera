# 避障识别（路线 A：区域 + 帧间差分）— 设计文档

日期：2026-09-28
状态：待用户复核

## 1. 背景与目标

已有的 `camera-test.py` 是一个摄像头调试工具：打开摄像头、1280×720 实时预览、灰度/边缘滤镜、截图、镜像、FPS 显示，已针对本机摄像头调到 1280×720 @ 30fps（后端 CAP_MSMF）。

本次要在此基础上往前走一步：**用摄像头做图像识别，服务于「避障」，但只做识别，不做控制。**

目标边界由用户明确划定：
- 只做到「识别」这一步——判断有没有障碍、障碍在哪一侧；
- 不做电机、舵机、串口等任何控制输出；
- 第一阶段在电脑上测试，**摄像头固定不动**；
- 未来想装到小车上「边开边避障」，但那属于后续迭代，不在本次范围内。

## 2. 范围

### 做
- 一个独立脚本 `obstacle_detect.py`：摄像头实时画面 + 左/中/右分区障碍判断
- 画面上可视化判断结果（哪一侧有障碍）
- 终端打印状态变化
- 几个现场可调的参数（主要通过按键实时调整，因为阈值必须对着真实画面标定）

### 不做（YAGNI）
- 距离估计（单目测距是独立难题）
- 物体分类/识别是什么东西
- 录像
- 串口/网络/控制层输出
- 移动场景的全局运动补偿

### 不改动
- `camera-test.py` 一行都不动。理由：它是「相机调试工具」，职责不同；且需要保留一个干净的、保证能打开摄像头的工具，用于排查「是相机的问题还是识别代码的问题」。

## 3. 技术路线与理由

在三条候选路线中选定 **A：传统 CV 的区域划分 + 帧间差分**。

| 路线 | 做法 | 为什么没选 |
|---|---|---|
| **A 传统 CV（选定）** | 相邻帧求差 → 二值化 → 按列统计变化 | — |
| B 目标检测（YOLO） | 预训练模型框出人/车/椅 | 只认训练过的类别；避障恰恰要发现未知障碍；CPU 上帧率低 |
| C 单目深度估计 | 模型输出每像素远近 | 算力要求高（CPU 上 1~3fps）；本机跑不动 |

选 A 的三个理由：
1. `camera-test.py` 中已画出的 1/3、2/3 两条竖线，正是分区骨架，改动增量最小；
2. 零新增依赖（只用 OpenCV），避开入门阶段最耗时的环境配置问题；
3. 帧差法不挑类别，天然能发现「没见过的障碍物」。

## 4. 适用边界（重要）

帧间差分的本质是「找两帧之间变化的位置」，因此：

| 场景 | 表现 |
|---|---|
| 摄像头固定，障碍物移动/靠近 | ✅ 正常工作 |
| 摄像头固定，障碍物静止（如一面墙） | ❌ 检测不到，画面从未变化 |
| 摄像头自身移动（小车行驶中） | ❌ 全画面都在变化，全部区域误报，方法失效 |

**因此本设计明确限定用于摄像头固定、监测一个方向的场景。**

- 「摄像头移动」的情况需要光流补偿或换路线 B/C，属于后续迭代。
- 「静止障碍检测不到」可用 OpenCV 自带的背景建模 `createBackgroundSubtractorMOG2` 缓解，但会引入「背景模型需要建立期」等新问题，**本次不做**，见第 9 节。

## 5. 架构

单文件 `obstacle_detect.py`，结构如下（沿用 `camera-test.py` 的分段注释风格）：

```
可调参数区（文件顶部，集中所有常量）
    WIDTH / HEIGHT          摄像头分辨率
    ZONES                   分区数量
    DIFF_THRESHOLD          二值化阈值（变化多大算变化）
    MIN_PIXELS_RATIO        每区判定为「有障碍」所需的最小变化像素占比
                            （默认 0.03；运行时可按键 [ ] 现场调整）
    CONFIRM_FRAMES          连续命中多少帧才确认（防抖）
    GLOBAL_CHANGE_RATIO     全局变化超过此比例则判定为光照/运动干扰，整帧忽略

open_camera(index) -> cap
    复用 camera-test.py 的逻辑：Windows 优先 CAP_MSMF，失败退回 CAP_DSHOW，
    再失败用默认后端；都失败则给出中文提示并退出。

detect_zones(prev_gray, gray, diff_threshold=DIFF_THRESHOLD) -> (ratios, mask)
    纯函数，不碰摄像头、不碰窗口。二值化阈值走默认参数，既能直接用全局常量，
    又能在测试时单独传入不同阈值。
    输入：上一帧灰度图、当前帧灰度图
    输出：每个分区的变化像素占比列表、以及用于显示的二值图
    —— 识别逻辑集中在这里，将来替换算法（MOG2 / 深度估计）只需改这一个函数。
    —— MIN_PIXELS_RATIO 的判定与 CONFIRM_FRAMES 的防抖都放在 main()，
       让本函数保持纯粹、便于测试（实现时对第 5 节的这处修正）。

main()
    主循环：取帧 → 镜像 → detect_zones → 判定 → 可视化 → 按键处理
```

### 为什么把 detect_zones 抽成函数
避免识别逻辑和摄像头/窗口代码纠缠在一起。这样：
- 逻辑可以单独测试（喂两张构造的图，检查返回值）；
- 将来上小车要换算法时，只替换这一个函数，其余不动；
- 用户的现有单文件风格得以保留，不需要引入包/模块结构。

## 6. 数据流（每帧）

```
cap.read() 取帧
  → 可选镜像 flip
  → cvtColor 转灰度 gray
  → [首帧无 prev，跳过检测，只记 prev=gray]
  → cv2.absdiff(prev_gray, gray)        得到差异图
  → GaussianBlur                          去掉传感器噪点
  → threshold(_, DIFF_THRESHOLD, ...)     二值化：变化够大 = 255
  → morphologyEx(OPEN)                    去掉零散白点
  → 全局变化统计：白色像素总占比 > GLOBAL_CHANGE_RATIO ?
        是 → 判定为光照突变/整体抖动，本帧全部区域强制判为「无障碍」
  → 按列切成 ZONES 份，逐份统计白色像素占比
  → 每份占比 > MIN_PIXELS_RATIO → 该区「本帧命中」
  → 连续命中帧数 >= CONFIRM_FRAMES → 该区状态 = 有障碍
  → 状态有变化时才 print，避免刷屏
  → prev_gray = gray
  → 可视化 + imshow + waitKey
```

## 7. 可视化与交互

画面元素：
- 保留分区竖线，颜色随状态变化：无障碍=绿，本帧命中（未确认）=黄，已确认有障碍=红
- 每区顶部画一个状态条
- 左上角文字：`thr:变化阈值  min:最小占比  zones:分区数  debug:开关`
- 第二行文字：每一区的**实时占比**（形如 `左:0.004  中:0.021  右:0.001`）

按键：
| 键 | 作用 |
|---|---|
| `q` | 退出 |
| `+` / `-` | 调整 DIFF_THRESHOLD（现场调敏感度，必须边看画面边调） |
| `[` / `]` | 调整 MIN_PIXELS_RATIO（现场压制 / 放开噪声误报） |
| `d` | 切换显示二值调试图（看清「算法到底看到了什么」） |
| `m` | 开关镜像 |

把 `+` / `-`、`[` / `]` 和 `d` 列为必备项，理由：这类阈值型算法**无法靠猜定参数**，必须看着真实画面调；调试视图能让用户直观理解算法每一步的结果，这也是本项目的学习目的之一。

画面上显示每区**实时占比**，是实现阶段实测后补上的关键功能：画面静止时那个数字就是**噪声水平**，判定阈值（`min`）必须明显高于它。没有这个数字，用户只能盲猜——实现阶段正是因为没有它，出现了「反复调参却在两个批次里得出相反结论」的情况（同一参数在一批素材里 0% 误报、在另一批里频繁报警，因为噪声会随光照间歇性升高）。

## 8. 错误处理与已知失败模式

- 摄像头打不开：沿用 `camera-test.py` 的中文提示并退出；
- `cap.read()` 连续失败超过 30 帧：打印提示后退出，避免死循环刷屏；
- 首帧没有上一帧：跳过检测；
- **光照突变**（开/关灯、有人影掠过造成的整体明暗变化）：由 `GLOBAL_CHANGE_RATIO` 兜底，整帧忽略；
- **摄像头自动曝光调整**：会造成全画面缓慢变化，由 `DIFF_THRESHOLD` + `GLOBAL_CHANGE_RATIO` 双重过滤；
- **误报与漏报是必然存在的**，本设计不追求零误报，而是通过可视化让用户看清误报来源，再针对性调参。

## 9. 验证方法（怎样算成功）

手动验收，三条：
1. 手在镜头前从左向右移动 → 终端依次报出「左 → 中 → 右」；
2. 画面完全静止 → 持续报「无障碍」；
3. 反复开关房间灯 → 不应报出障碍（或仅极短暂命中，不应确认）。

以及一条工程验证：
4. `detect_zones` 可用构造的两张图直接调用，返回的占比符合预期（无需摄像头即可验证核心逻辑）。

## 10. 后续演进（不在本次范围）

按优先级：
1. **静止障碍检测**：换用 `createBackgroundSubtractorMOG2`，需处理背景模型建立期与「障碍物停留过久被并入背景」的问题；
2. **移动场景**：光流补偿（`calcOpticalFlowFarneback`）或换用路线 C（单目深度估计）；
3. **控制层对接**：把「左/中/右 + 置信度」输出成固定格式（打印行/文件/串口），供控制器读取。

## 11. 未决问题

- **阈值标定仍未完成**：`MIN_PIXELS_RATIO` 默认 0.03、`DIFF_THRESHOLD` 默认 25，是实测得出的起点。
  实测数据：画面静止时噪声占比在 **0.002~0.026** 之间波动（随光照间歇性升高），
  所以 0.03 只是「压得住多数情况」的折中。**仍需在你的目标场景里标定**——
  画面上的实时占比就是依据（静止时的数字 = 噪声水平，阈值必须明显高于它）；
- 灵敏度取舍未定：避障通常「宁可误报，不可漏报」，若实测发现漏检（手挥过不报警），
  说明 `min` 偏高，应按 `[` 调低。这个取舍只有你能定；
- 分区数先用 3（左/中/右），若发现精度不够再考虑 5 区；
- 是否需要把结果同时写进日志文件——待第 3 步「控制层对接」时再定。
