## 1. 背景与目标

用摄像头做图像识别，服务于「避障」，但**只做识别，不做控制**。

- 阶段一：在电脑上运行，摄像头**固定不动**
- 阶段二（未开始）：装到小车上，边移动边避障

## 2. 决策演变：为什么放弃帧差法

项目最初选的是「区域划分 + 帧间差分」（`absdiff` 相邻两帧）。它在实测中暴露了两个问题，最终被放弃。

### 2.1 根本缺陷：检测不到静止障碍

帧差法比较的是**相邻两帧**，检测的是「画面此刻是否在变化」，而不是「画面里有没有东西」。后果：

| 场景 | 帧差法的表现 |
|---|---|
| 障碍物出现后**静止** | ❌ 判定消失——画面不再变化 |
| 一堵始终在那里的墙 | ❌ 从不报警 |
| 慢慢移动进来的物体 | ✅ 能报警，但**一停住就变回「无障碍」** |

更糟的是：防抖要求连续 3 帧命中，而「物体出现」只造成 1 帧变化，**可能连报警都触发不了**。

这个缺陷无法靠调参解决——它是方法本身的性质（帧差法没有记忆）。

### 2.2 阈值困境

实测（本机摄像头，1280×720）：画面静止时噪声占比在 **0.002 ~ 0.026** 之间波动，随光照间歇性升高。

判定阈值必须高于噪声，但噪声本身在变，于是同一个阈值在不同时间表现完全不同：
- 一批素材里 0% 误报
- 另一批素材里频繁误报

这是「无法标定」的问题，不是「标定得不够好」的问题。

### 2.3 结论

帧差法只能回答「有没有东西在动」，而避障需要回答「有没有东西、有多近」。**两者问题不匹配。**

相关代码（`obstacle_detect.py`、`tests/`）与实施计划已删除，git 历史中仍可查。

## 3. 选定方案：深度估计 + 目标检测

**两层分工，各做自己擅长的事：**

```
摄像头帧 ──┬─→ 深度估计 ──→ 每个像素的远近 ──→ 「有没有、有多远」（不挑类别，静止也管用）
           └─→ 目标检测 ──→ 框 + 类别      ──→ 「那是什么」
```

| | 深度层 | 检测层 |
|---|---|---|
| 回答 | 有没有东西、大概多近 | 那是什么 |
| 静止障碍 | ✅ 管用（推理单帧，不依赖帧间变化） | ✅ 管用 |
| 类别限制 | 无（墙、树枝、塑料袋都算） | ❌ 只认训练过的类别（COCO 80 类） |
| 必要性 | **是主判断** | 辅助信息 |

关键点：**检测层是配角**。避障最怕「没见过的障碍物」，而检测层恰恰只能认已知类别；深度层才是不挑类别的那一半。

## 4. 现有实现

文件：`depth_demo.py`（双窗口实时 demo）

```
load_models()            把两个模型加载到 GPU（fp16 半精度）
estimate_depth(proc, model, bgr)
                         整幅画面的远近图 → uint8 灰度（越亮 = 越近）
                         —— 归一化在 GPU 上做完，只把 1/4 大小的数据拷回 CPU
detect(proc, model, bgr, threshold)
                         目标检测 → 框 + 类别 + 置信度，坐标已换算回原图尺度
main()                   主循环：
                         深度每帧都算；检测每 DETECT_EVERY_N 帧才算一次，
                         但结果被缓存、每帧照画 —— 所以框不会闪，只是位置最多滞后 3 帧
```

可见参数（文件顶部）：

| 常量 | 默认 | 含义 |
|---|---|---|
| `DETECT_THRESHOLD` | 0.5 | 检测置信度门槛 |
| `DETECT_EVERY_N` | 3 | 每几帧跑一次检测 |
| `CAM_W` / `CAM_H` | 1280 / 720 | 摄像头分辨率 |

按键：`q` 退出 · `n` 开关检测框 · `m` 开关镜像

## 5. 实测数据

**本机环境**

| 项 | 值 |
|---|---|
| 显卡 | NVIDIA GeForce RTX 4070 Laptop GPU |
| Python | 3.12.8 |
| torch | 2.6.0+cu124 |
| transformers | 5.14.1 |
| 摄像头 | 1280×720 @ 30fps（CP_MSMF 后端） |

**模型**（均从 `hf-mirror.com` 下载，存放于项目目录之外）

| 用途 | 模型 | 体积 |
|---|---|---|
| 深度 | `depth-anything/Depth-Anything-V2-Small-hf` | ~95 MB |
| 检测 | `PekingU/rtdetr_r18vd` | ~77 MB |

**性能**（同一批录制帧 + `torch.cuda.synchronize()` 强制同步后测量）

| 项目 | 耗时 | 说明 |
|---|---|---|
| 深度（fp32，初版） | 52.0 ms | |
| **深度（fp16）** | **23.0 ms** | 提速 56%，是当前主要开销 |
| 检测（fp16） | ~9 ms | 隔 3 帧摊薄后约 3 ms |
| **综合** | **34.6 ms → 28.9 FPS** | 优化前为 63.4 ms → 15.8 FPS |

**fp16 的精度代价**：归一化后逐像素平均绝对差 0.00019、最大差 0.0031（<0.3%），视觉上不可辨。

> ⚠️ 测量陷阱（曾经踩过）：CUDA 是**异步**执行的，不在计时点调用 `torch.cuda.synchronize()` 会测出偏小的耗时，从而得出「优化后反而更慢」的假结论。此外，对比不同参数时必须用**同一批录制帧**，否则摄像头读帧时间的波动会污染结果。

## 6. 已知限制

1. **输出的是相对深度，不是米数**。Depth Anything V2 普通版给出的是相对逆深度（值越大 = 越近），**没有物理单位**，因此不能直接判断「1 米内有障碍」。要真实米数需换 Metric 版模型。
2. **检测层只认 COCO 80 类**，且远处/半身目标的置信度天然偏低——这不是误检，是正常表现（实测确认）。
3. **运动模糊**：深度估计是单帧推理，理论上不依赖帧间关系，因此**相机自身移动不会像帧差法那样直接失效**；但移动带来的模糊会降低深度质量，**尚未实测验证**。
4. **帧率 29 FPS 是上限**，瓶颈在深度推理（占 66%）。要进一步提速需降低模型输入分辨率，那会真实损失精度。
5. **未验证的适用边界**：强光照、纯白墙面、镜面/透明物体等对深度模型的已知难点，均未测试。

## 7. 待决定的设计问题

判定逻辑**尚未设计**——现在的 demo 只显示，不做任何「有障碍 / 无障碍」判断。要实现判定，必须回答：

1. **怎么从深度图得出结论？** 是把画面分左/中/右取各区最近的深度值？还是做「可通行区域」检测？
2. **阈值怎么定？** 相对深度没有物理单位，阈值只能对着场景标定（这曾是帧差法的痛点，需评估这里是否同样棘手）。
3. **要不要换 Metric 版模型？** 换来真实米数（可判断「1 米内」），代价是模型更大、精度受训练域限制（室内/室外分版）。
4. **检测层是否参与判定**，还是只做显示？
5. **输出形式**：屏幕高亮 / 终端打印 / 将来给控制层的固定格式？

## 9. 附：术语对照

| 术语 | 含义 |
|---|---|
| 相对深度 | 只说 A 比 B 近，没有物理单位 |
| 度量深度（Metric） | 输出近似真实距离（米） |
| fp16 / 半精度 | 用 16 位浮点代替 32 位，速度翻倍、精度略降 |
| 帧间差分 | 比较相邻两帧找变化——本项目已放弃的方法 |
